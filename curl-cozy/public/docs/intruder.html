Intruder

Intruder sends a request repeatedly with a different payload at one selected position. Send a request from HTTP History, Replay or Intercept through its context menu, or enter a request directly.

Mark a position

Select text in the URL, a header value or the body, then click Mark selection. You can also type paired markers directly: https://example.com/items/§123§. Exactly one pair is supported. Each payload replaces the entire marked value. Header names cannot contain markers.

Payload sources

  • Manual list: one payload per line, up to 10,000 values.
  • Numbers: inclusive integer range with a positive or negative step and optional zero padding. Values use signed 64-bit integers without JavaScript precision loss. Up to 1 million values are generated lazily.
  • TXT / CSV: select a local UTF-8 file, choose a CSV column and whether the first row is a header, and import. Quoted CSV fields, commas and multiline values are supported. Files stream in small batches into the local backend database; execution fetches pages of 128 values. No arbitrary server file paths are accepted.

Files require a saved workspace. Limits: 256 MB input file, 16 KB per payload, 64 KB per record, 1,000 CSV columns, 1 million values per file, 20 files and 128 MB payload text per workspace. Incomplete imports can be deleted. Empty values can be retained by turning off Skip empty payloads.

Encoding and profiles

Choose none, URL component, UTF-8 Base64, UTF-8 Hex or HTML escaping. Preview shows payload substitution using current variables and the selected profile; it does not send a request. Variables and profile headers resolve before payload substitution, so a payload containing {{token}} remains literal. A profile that replaces a marked Authorization or Cookie header removes the position and blocks the run. Cookie responses update the selected profile jar. Concurrent responses may update the same cookie; use concurrency 1 when sequence matters.

Run controls

Start offset is zero-based. Request limit is up to 100,000 per run, concurrency 1–10, rate 1–100 request starts per second and minimum delay up to 60,000 ms. The rate and minimum delay apply globally across workers. Pause blocks pending sends; Stop stops scheduling and waits for in-flight responses. Already sent requests may have changed server state.

The existing Replay sender only permits public HTTPS destinations, does not follow redirects and retains its timeout and response-size limits. This version does not execute Replay scripts or chain Flows.

Results and storage

Search payloads, filter by HTTP status, match or errors, and sort by index, status, size or duration. Click a row to view the actual request and response preview; right-click the request to send it to Replay or copy cURL. Match text is a case-sensitive literal search over the full returned response before truncation.

Saved-workspace results and requests persist locally, with 100 results per page and 50 runs per history page. Response previews retain the first 32,768 characters and bounded headers, with full returned size and a body SHA-256 when browser cryptography is available. Truncation is shown explicitly. Evidence includes credentials; delete runs when no longer needed. There is no automatic history expiration.

Each saved run has a 28 MiB evidence scheduling budget (32 MiB backend cap). Space is reserved for in-flight requests. A run stops when there is insufficient room; continue with a later source offset in a new run. Temporary runs support at most 200 requests and an 8 MiB evidence budget; only five recent runs remain in browser memory.

Keep this browser open to execute a run. Navigation within the app preserves the runner, while changing workspace stops scheduling. Closing or reloading the browser interrupts execution; unfinished saved runs never resume automatically. A failed evidence write stops new sends. Retry evidence saving writes captured results only and never repeats HTTP requests.
