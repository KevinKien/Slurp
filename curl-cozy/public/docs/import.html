Importing requests into Replay

Requests can be imported from cURL, Postman collections, Bruno files and Burp exports. Open Replay and use the toolbar buttons: Import Postman, Import Bruno, Import Burp or Import cURL. Each selected request becomes its own Replay tab.

Parsing happens in your browser. Files are never uploaded, and no imported request or script is executed until you click Send.

cURL

Paste a cURL command and choose Import request. The command is parsed as text; it is never executed by a shell. The result replaces the request in the active tab.

Postman

  • Accepts Collection v2.0 or v2.1 JSON, up to 10 MB and 500 requests.
  • Folders become tab names such as Auth / Login. An optional environment JSON can be imported at the same time; environment values take precedence over collection values.
  • Existing workspace variables are kept unless you enable Overwrite existing workspace variables.
  • Postman scripts and protocol options are shown for reference only. They are not converted or executed. Basic and bearer authentication are converted to an Authorization header.

Bruno

  • Select one or more .bru request files (2 MB each, 10 MB total, 500 files) and an optional environment .bru file.
  • Only raw JSON, text, XML and SPARQL bodies are supported. Collection and folder inheritance is not available in standalone files, so set explicit authentication and body modes before exporting.
  • Request-scoped variables, assertions, scripts and response extractors are not imported; convert them to Replay variables or an After response script manually.

Burp

In Burp, select the Proxy history, Repeater or Site map items you need, right-click and choose Save items, then keep Base64-encode requests and responses enabled. Import the saved XML with Import Burp.

  • The item comment becomes the tab name. Items without a comment are named METHOD /path, and duplicate names get a numeric suffix.
  • The Host header, item host, port and protocol are combined into the request URL. Absolute-form request targets are kept as sent.
  • Connection framing headers are removed because the URL and body define what Replay sends: Host, Content-Length, Transfer-Encoding, Connection, Proxy-Connection, Keep-Alive, Upgrade, TE, Trailer and Expect. The import lists them in a warning.
  • Repeated header names keep the first value and report the duplicates. Requests with invalid header names or values are disabled with a warning.
  • CONNECT tunnels, unsupported methods and non-HTTP request targets are disabled with a warning. Only the request side is imported; captured responses are ignored.
  • Request bodies must be text and at most 1 MB. Non-text bodies are imported with a warning, while gzip-compressed bodies are disabled because they cannot be represented as text.
  • Up to 10 MB, 5,000 items and 500 requests per export. Items with only a response are skipped; if nothing importable remains, the import reports why.

Burp project files (.burp)

A .burp project file is a proprietary binary format that PortSwigger does not publish, so it cannot be read directly. Slurp detects it and explains the options instead of guessing:

  • Export the items you need as XML from Burp and import that file, or
  • Convert the whole project with the community prub tool (prub export project.burp export.json) and import the resulting JSON. Slurp reads its proxy, repeater and target entries, and Repeater captions become tab names.

Project request bytes do not record the URL scheme, so those URLs default to http. Change them to https in the URL field when the traffic used TLS.

Variables and limits

  • Imported requests keep {{variable}} syntax where the source format used it. Missing variables are listed before import; add them under Variables before sending.
  • Replay holds up to 100 tabs per workspace, so the number of selectable requests is capped by the free slots. Close tabs to import more.
  • Each import is stored in the selected workspace with the other tabs. Temporary sessions keep imported tabs in memory only.
  • Replay sends requests through the Rust backend with the same HTTP(S) validation, DNS pinning, redirect policy, response size limit and timeout as any other send.
