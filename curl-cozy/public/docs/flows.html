Flows

Build and test sequential API workflows: login → 2FA → account creation → verification → onboarding. Each run uses an independent copy of its flow definition and initial variables.

Create a flow

  1. Open Flows and click New flow. Rename it, then add a blank step or copy a request from a Replay tab. Imported Postman and Bruno requests can be copied from Replay.
  2. Edit each request and click Apply step changes. Changes in the editor must be applied before running or selecting another step. Applying changes affects future runs; active runs keep their original snapshot.
  3. Open Initial variables to add values such as base_url, username and password. You can explicitly copy Replay variables into the flow. Flow and run updates never modify Replay variables.
  4. Drag steps or use their arrow buttons to change execution order. Click Run flow to start sending requests.

Extractors, checks and scripts

  • Expected status: 2xx by default. Use a code such as 200, a list such as 200,201, or leave empty to accept any HTTP response.
  • JSON checks: Exists checks whether a path is present. Equals compares against a JSON literal or plain text. Contains checks whether a string includes the expected text.
  • Extract variables: read JSON paths, response headers (case-insensitive) or the full text body. Dot paths, numeric array indices and JSON pointers are supported: data.token, items[0].id, /data/token. JSONPath filters and arbitrary expressions are not supported. Extracted values become strings; objects are serialized as JSON.
  • After response: the same isolated synchronous JavaScript API as Replay Scripts. Extracted variables are available to the script. Script updates affect this run only.
  • All variable changes from a step commit together only when its checks, extractors and script succeed. On failure, the previous variables are preserved. The HTTP response remains available.
  • On failure: stop by default, or explicitly continue to the next step. A run with any failed step is marked failed even if subsequent steps succeed.

Pause and test different paths

  • Pause before a step to enter OTP or change run variables. Click Continue run to send it, or Skip paused step to test omission.
  • Disable a step to skip it in future runs, or reorder steps to test business logic.
  • Run step runs only that step using flow initial variables. Run until here starts from the beginning and stops after the chosen step.
  • From a recorded result, Re-run this step or Run from this step creates a new run with the variables captured before that step. Continue checkpoint as new run uses the last recorded variables and starts at the next unfinished step.
  • Clone flow copies a definition. Clone run to flow copies the run's original definition and initial variables, so you can edit a variant for user B or another test case.

History and comparison

Runs & comparison stores the flow snapshot, resolved requests, responses, checks, script logs and variables before/after each step. Choose another run to compare status, timing, request changes and response changes. Inspect request or response content side by side. Comparisons match step IDs first, then positions for cloned flows. Viewing history never sends requests.

Checkpoints restore client-side variables only. They do not roll back accounts, consumed OTPs or other server changes. Re-running a step sends another real request; use fresh test data or explicitly configured cleanup requests as needed.

Execution and storage

  • Execution runs in the current browser session. Navigating within the app preserves a running or paused flow. Keep the browser open to complete execution.
  • Switching workspaces stops the active run before any further steps are sent. Checkpoints are saved to the workspace where that run started.
  • Stop prevents subsequent steps and variable commits. It cannot undo or reliably cancel an HTTP request that has already been sent.
  • Definitions and checkpoints are saved to the selected workspace. Temporary sessions keep them in memory and lose them on reload. Definitions and history show storage errors with retry controls.
  • Reloading does not automatically restart requests. A saved running run is shown as interrupted; explicitly continue it as a new run or clone it to test again.
  • Only one flow runs at a time. Requests use Replay's HTTP(S) validation, response size limit and configured timeout; select an authentication profile to share its cookie jar between steps. Without a profile, pass needed tokens or headers explicitly. See Profiles and Response Diff.

Limits

Up to 50 flows per workspace, 50 steps per flow, 20 extractors and 20 JSON checks per step. Definitions are limited to 5 MB per workspace. A run supports up to 100 variables, 64 KB per value and 256 KB total serialized variables. Large runs stop after reaching the 8 MB checkpoint budget; continue from that checkpoint as a new run. Stored run data is bounded to 32 MiB. The history list loads 50 summaries at a time and fetches full run data on demand.
