Account Profiles, Response Diff and Authorization Matrix

Use separate account identities to test API access and compare evidence. These features use the existing Replay sender: public HTTPS hosts on port 443, no automatic redirects, a 2 MB response limit and the request timeout from Settings.

Profiles · Cookies · Response Diff · Authorization Matrix · Scripts reference

1. Create an account profile

  1. Choose a saved workspace, then open Profiles → New profile.
  2. Name it User A. Add each allowed HTTPS origin on its own line, such as https://api.example.com. Origins have no trailing slash or path.
  3. Add variables as a JSON object of strings. For token authentication, initialize {"token":""}.
  4. Add headers, for example {"Authorization":"Bearer {{token}}"}, then select Apply profile.
  5. Create a separate profile for User B or Admin. Cloning a profile copies its headers and variables, but starts with an empty cookie jar. Replace copied credentials before sending.

Select an authentication profile in Replay or Flows. The selection is shared within the workspace. None (request credentials) uses the request's original headers and shared Replay variables. With a profile selected, its variables override shared Replay variables, Authorization and Cookie headers from the template are removed, and the profile's headers and matching cookies are applied. Requests outside the profile's allowed origins are rejected before sending.

Save a login token to the selected profile

In Replay → Scripts → After response:

const body = response.json();
if (response.status === 200 && typeof body.access_token === "string") {
  variables.set("token", body.access_token);
}

Send the login request with User A selected. Successful script updates go to User A's variables, leaving User B and shared Replay variables unchanged. Switch to User B to log in separately. Without a profile selected, scripts continue updating shared Replay variables.

Use a profile in Flows

The profile is snapshotted at run start. Its variables initialize the run, and its headers are resolved from the current run variables before every step. Cookie responses are available to the next step. Extractors and Flow scripts update isolated run variables; they do not automatically overwrite profile variables. A checkpoint keeps its recorded run variables when rerun with the recorded profile. Stop or finish a run before testing a different identity.

2. Cookie jars

Each profile has its own jar. Set-Cookie headers are captured individually, including Expires values containing commas. Matching considers host/domain, path, Secure and expiration. Max-Age takes precedence over Expires. Expired/deleted cookies stop being sent. Public suffix domains and unrelated domains are rejected. HttpOnly, SameSite and cookie prefixes are recorded; __Secure- and __Host- restrictions are enforced.

This is an HTTP testing client, so HttpOnly cookies remain available to the tool and SameSite is not enforced as a browser navigation policy. Session cookies persist with a saved workspace until removed or expired. The browser's own cookies are never imported automatically. Use Profiles → Cookie jar to inspect metadata, remove individual cookies or clear the jar.

Profiles, including tokens, headers and cookie values, are stored in the local workspace database without application-level encryption. Temporary profiles stay in browser memory and are lost on reload. Workspace changes prevent late responses from updating another workspace's profiles. A save conflict from another browser is reported; Reload profiles discards local unsaved edits and reads the latest saved version.

3. Response Diff

  • Replay: use Compare previous after multiple sends.
  • Replay Send history: select a send and another send to compare.
  • Flows Run history: select a comparison run and step, then Compare step responses.
  • Authorization Matrix: select a result cell and Compare with baseline.

Status, headers and body are compared separately. JSON object keys are sorted, while array order is preserved. Non-JSON text preserves whitespace except CRLF normalization. Enter ignored header names and exact JSON paths separated by commas. Examples: timestamp, data.updatedAt, items[0].id, /data/requestId. Wildcards are not supported. Default ignored headers are Date, Set-Cookie, X-Request-ID and X-Correlation-ID; clear the list to compare them.

Highlighted changes show at most 700 lines per body. Equality is computed from the full normalized response; switch to Full normalized bodies to inspect beyond the preview.

4. Authorization Matrix

  1. Prepare account profiles and requests in Replay.
  2. Open Authorization Matrix, select requests and profiles, and optionally include Anonymous.
  3. Select a baseline account, normally the account expected to access the resource.
  4. Set each cell's expected access to Allow, Deny or Observe. Add JSON paths to ignore if needed.
  5. Select Run matrix. Each selected cell sends a real request, sequentially.
  6. Click a result to inspect the actual sent request and response, then compare with the baseline.
ExpectationInterpretation
Allow2xx passes the status check; other outcomes require review or are inconclusive.
Deny401/403/404 passes the status check; 2xx is flagged for review.
ObserveA successful response with the same normalized status and body as a successful baseline is flagged for review.
InconclusiveTransport errors, redirects, 429 and 5xx require manual inspection.

Matrix removes Authorization, Cookie and profile-managed headers from templates before applying each identity. Credentials embedded in request URLs, bodies or shared variables remain: inspect anonymous requests to ensure they are actually unauthenticated. Requests retain their resource IDs across profiles so cross-account access can be tested. Profiles may intentionally override a resource variable, so inspect the sent URL as well.

Scripts are not executed by Matrix. Cookies remain separate for each profile and can update from responses. Stop waits for the in-flight request to return and prevents subsequent requests; it cannot undo server actions. Changing workspace stops further cells. Runs survive in-app navigation while the browser remains open; reloading does not automatically send anything.

Limits: 20 requests, 30 profiles, 200 cells and a 2 MB configuration. Evidence stops before another request once it exceeds an 8 MB budget. Snapshots with unusually large headers or JSON-escaped bodies are explicitly truncated and marked inconclusive; they are excluded from baseline comparison. Saved workspaces retain the latest 50 completed/stopped/failed matrix runs; history includes the actual sent credentials and responses. Temporary results stay in memory. A review flag is a lead, not proof of a vulnerability: inspect application error bodies, intended public data and expected business rules.
