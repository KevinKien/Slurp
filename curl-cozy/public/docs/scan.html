Scan dashboard

The dashboard shows running and paused tasks, recent scan history and findings. Use task controls to pause, resume or stop the active scan. Search findings by title or endpoint, filter by severity and status, and choose View evidence to open verification details. Saved findings are paginated and scoped to the selected workspace.

Right-click a request in HTTP History, Replay or Intercept and choose Scan passive or Scan active. The full request opens in a configuration dialog above the dashboard. Choosing either action opens configuration; it does not send requests automatically.

Automatic capture audit

New completed proxy captures are audited after History storage, in the backend while Slurp runs. Existing History is not backfilled. Target Scope applies. Dashboard provides a global pause/resume control and queue/completion/skipped/error counters. Automatic auditing is enabled by default; runtime controls reset on restart.

API candidates receive up to two probes: one removes common authentication headers, cookies and token query parameters; the other sets Origin: https://evil.com. Original methods and bodies are retained, so probes can repeat state-changing operations. HTTP 200 produces a NoAuthen finding requiring review. Wildcard or reflected Access-Control-Allow-Origin also requires review; neither alone proves a vulnerability. Body credentials and custom authentication may remain.

Captured JavaScript is analyzed without execution or fetching discovered URLs. Dashboard lists endpoint candidates and suspected usernames/passwords, API keys, tokens and private keys, with source coordinates and masked credential excerpts. Original source and local evidence may still contain secrets. Search findings by endpoint or credential type. Relative URLs and method hints require application context; credentials are not tested for validity.

Limits: 2 MB UTF-8 identity-encoded source, 20,000 literals, 8 KB per literal and 400 findings. Incomplete empty checks are inconclusive; compressed/binary captures are skipped. Literal analysis can miss comments, obfuscated, concatenated and runtime-generated values. No source-map discovery or crawling is performed. The independent Rust implementation is inspired by js-link-finder and js-miner, rather than a full port.

Results belong to the original workspace; temporary automatic results disappear when Slurp stops. Probes do not enter History or trigger recursive scans. The following sections describe manual scans.

Scan profiles

Choose the separate passive or active action from the request menu, then select a saved profile. Create or edit profiles to choose checks. The engine retains combined Both mode for legacy/programmatic plans. Select parameters for parameter checks. Passive observations now include CSP, HSTS, framing, Content-Type, transport/URL credentials, private-key markers, directory indexes and OpenAPI signatures.

Additional active checks cover repeated SQL error differentials with controls, marked template arithmetic with invalid-syntax controls, parameter-based file traversal with content signatures, and two-destination redirect Location verification. These findings require review. Time or evidence limits can leave remaining checks incomplete. Stored XSS, extended OAST workflows, request smuggling, the full Burp issue catalog is not implemented.

Passive inspects an existing captured response without probing the target; the optional OSV dependency check queries package/version advisories externally. History requests with a response use this mode by default. Cookie checks need separate Set-Cookie fields; collapsed headers are reported as inconclusive.

Active sends repeated baseline, probe and control requests through the Replay sender. Select a scan profile and any required parameters. Advanced request settings contain timing and rate controls. Enable the sending checkbox and click Start scan. Repeated requests may change application state. Requests without an existing response require active mode. HTTP(S), localhost and LAN targets are supported; Replay timeout/response limits apply.

Checks and parameters

  • Cookie flags: observe missing Secure/HttpOnly attributes. Cookie purpose still matters.
  • Response headers: inspect successful HTML documents for nosniff.
  • Error disclosure: look for supported internal-error signatures; example text can cause false positives.
  • Input reflection: test two independent markers in selected inputs. Reflection does not establish XSS.
  • Input error handling: compare stable baselines, malformed input, repeat probe and original-value control. Reproducible errors do not establish injection.
  • CORS origin handling: test two untrusted Origin values. Browser verification is still required.

Reflection and input-error checks require explicit query, form-urlencoded or JSON scalar parameter selections, up to ten. Duplicate query occurrences are listed separately. JSON field names use escaped JSON pointers. Form-urlencoded fields are supported, including duplicate fields; unrelated encoded fields are preserved. Multipart mutations are not supported.

HTTP active checks

Phase 3 adds controlled SQL boolean comparisons, bounded MySQL timing, CRLF response-header injection, anonymous/invalid-credential comparisons, Referer/client-IP trust, URL override routing and OPTIONS/TRACE diagnostics. SQL timing is an intrusive check that must be explicitly selected in a profile. Traversal includes additional encoding layers, redirect checks include protocol-relative URLs, and wildcard CORS is a reviewable configuration observation.

Findings require repeat/control evidence. HTTP 200 alone, reflected body text and timeouts do not establish vulnerabilities. Anonymous access may be intentional; body/custom authentication can remain. URL override reports routing influence, not an authorization bypass. OPTIONS advertising PUT does not trigger a write. TRACE uses diagnostic headers without original application headers. Forwarded/X-Forwarded-* remain filtered; client-IP checks use X-Real-IP/X-Client-IP.

Only method-policy checks may change the selected method to OPTIONS/TRACE, retaining origin/path; CONNECT is unsupported. Anonymous/header-access/method diagnostic responses do not overwrite profile cookies. There is no total request-count limit; review skipped and inconclusive results caused by duration, evidence or check prerequisites. Cross-account BOLA, raw protocol, OAST and stored/browser attack engines are not included.

Scan policy and coverage

Select a saved scan profile, or use Create profile / Edit profile to choose checks. Profiles are stored in this browser and shared across workspaces. Intrusive checks are labeled; selecting one enables its required policy. Built-in active defaults exclude them. Sending consent remains required. Advanced request settings contain rate and timeout controls; all engine limits remain enforced.

Scan coverage lists implemented, experimental and planned modules with prerequisites and verification descriptions. Planned modules never execute. Selected-run coverage separates completed, skipped and inconclusive results and JavaScript endpoint discoveries. Module counts do not claim full Burp issue coverage.

Expanded passive audit

Cookie checks cover scope, duplicate identities, SameSite and __Host-/__Secure- rules. Disclosure checks cover database URIs, password-like fields and reflection, masked email/private-IP/SSN/card candidates, source/serialization markers, private JWK fields, GraphQL syntax and technology headers. Policy checks inspect selected CSP directives, charset/MIME and HSTS. These are observations requiring review, not confirmed exploits. Public examples and test values may match.

New body analyzers inspect at most 256,000 characters and retain masked finding excerpts; local evidence and History may still contain secrets. Separate cookie fields are required, with up to 100 processed. Analysis/evidence limits and combined CSP policies produce inconclusive results. Extended bundle dependency attribution, TLS certificate analysis and full browser taint analysis remain planned.

Run controls

Configure 2–3 baseline samples, a rate of 1–20 starts per second and minimum delay. Known dynamic JSON paths can be excluded from baseline comparison. Pause blocks pending sends. Stop prevents further scheduling; in-flight requests still complete. App navigation keeps the run alive, while changing workspace stops scheduling. Keep the browser open; unfinished scans do not survive reload.

Read results

Severity and confidence are separate. Verified refers only to the observation named in the finding and its recorded verification method. Suspected indicates a signature that needs confirmation. Needs review requires contextual or browser validation. Check skipped and inconclusive results even when there are no findings; absence of findings does not establish security.

Expand a finding for its explanation, verification method, excerpts, remediation and evidence. Request evidence supports the context menu, including Send to Replay and Copy cURL. Expand request/response panels to search their contents or compare a response with the baseline.

Evidence includes actual requests and credentials and is stored locally with the selected workspace. Response previews are bounded and truncation is shown. The engine has an 8 MB evidence budget and stops before sending requests it cannot retain. Saved run history can be selected, paginated and deleted. Temporary runs remain in browser memory.

A failed save can be retried with Retry evidence saving; it writes the captured evidence without sending HTTP requests again.

Specialized injection checks (phase 4)

Edit an active scan profile to select experimental command/code/EL, LDAP, XPath, XML or XXE checks. POSIX command probes use two split printf markers. Code/EL probes compare two computed products with quoted controls; intentional calculators may match. Parser checks require repeated specific errors absent from benign controls; generic HTTP 500 errors are insufficient.

XML internal entity processing is reported separately and does not establish XXE. Intrusive XXE probes compare repeated local-file signatures with escaped-entity, missing-file and original controls. Query/JSON parameter variants require explicit input selection. XML body variants require an XML media type and replace the whole body, so schema-dependent APIs may reject probes.

Command execution, code execution and local-file XXE checks are intrusive and excluded from built-in active defaults. No file writes, recursive entity expansion or external callbacks are performed. Windows command execution, blind/timing execution and arbitrary runtime contexts are not covered. Findings require review; file contents are omitted from excerpts but may remain in local evidence. Response analysis is bounded to 256,000 characters. Scans have no total request-count cap; duration and evidence limits still apply. Review skipped/inconclusive results.

SQL quote-repair comparison

The SQL error check also compares single/doubled/doubled/single quote suffixes. Repeated single-quote server errors must be repaired by doubled quotes restoring the stable successful baseline twice; the original request must restore it too. This detects some generic error pages without SQL error text. Findings remain possible SQL injection requiring review; reflection or arbitrary response differences are insufficient. Existing profiles using the SQL error check automatically receive this comparison.

JavaScript report deduplication

Within each workspace, previously reported endpoint/method pairs are omitted from later automatic JavaScript reports. New credential fingerprints distinguish different values. Duplicate-only captures create no report; later reports contain only new findings. Existing reports remain immutable. Deleting a report permits rediscovery.

CSP audit and highlighted finding evidence

The passive request/response audit checks unrestricted framing and inline styles allowed by enforced CSP. It considers style directive fallbacks, nonce/hash sources, multiple policies, and applicable X-Frame-Options. Report-Only policies do not enforce restrictions. These findings are informational and require contextual review.

Each finding has Request/Response tabs. Yellow highlights payloads and changed request lines, red highlights finding excerpts such as a CSP header, and green highlights response changes from the baseline. Large responses highlight the changed region. Compare baseline also shows deletions. The separate all-evidence section is removed; evidence remains in each finding.

SQL comparisons mask only the selected HTML input value to handle reflected filters. Both SQL error and boolean checks can use repeated numeric OR true/false pairs with two predicates, a repeated pair, and an original control. Both response groups must be internally consistent and distinct; the original must restore the baseline. This does not prove SQL execution.

Concurrent endpoint scans

Start another endpoint while existing scans run. Each task has its own execution, profile session and evidence. Use its Dashboard row to Pause, Resume, Stop or retry a failed save. A save failure does not block other scans. Request limits and timeouts apply per task. Tasks continue across page navigation; switching workspace stops outgoing scans and saves evidence in the original workspace. Finding evidence tabs wrap to fit the available width.

Passive scan from Replay

Choose Scan passive from a Replay tab or its request/response panel. Passive scanning uses the completed request and response snapshot, including the values actually sent. Later editor changes are not paired with that response. Scan active uses the current editor request. If no response exists, starting the scan automatically sends the resolved original request once in the background. Existing responses are reused. Fetch failures do not retry or produce findings.

Browser XSS validation (phase 5, initial scope)

In Scan active, edit or create a profile and select Reflected and DOM XSS (browser validation) or DOM XSS (script audit and browser validation). New browser installations include a Browser XSS profile. Existing profiles are preserved; Active standard excludes browser checks.

Install Chrome/Chromium on the Slurp host, or set SLURP_BROWSER_PATH to its executable before launching Slurp. Common macOS/Linux/Windows paths and Windows Edge are detected. Node.js and Playwright are not required. Missing browsers, worker contention and timeouts produce inconclusive results.

The engine uses the shared HTTP sender to obtain responses, then renders successful HTML snapshots up to 256 KB in a temporary headless browser profile. Original CSP remains enforced. Uncaptured secondary traffic and frames are blocked; the DOM check can use captured script snapshots; cookies and prior browser state are not reused. URL fragments are tested inside the browser without sending them to the server.

A verified finding requires two independent payload callbacks and non-executable/original controls that do not execute. Reflection alone is insufficient. Each finding includes Request/Response and Browser tabs with callback outcomes, markers, browser URLs, observed HTML sinks and security messages. Verification applies to the isolated snapshot.

This initial scope covers selected HTML/attribute/script-string contexts and inline-script DOM paths. Full taint analysis, dependencies outside bounded runtime discovery, user interactions and stored-XSS write/readback/cleanup workflows remain planned. Negative snapshot results are inconclusive for those paths.

DOM script audit before probing

The DOM XSS check first parses executable inline scripts and script files, follows bounded literal module imports and identifies URL source/sink candidates. It recognizes query names from URLSearchParams, selected aliases/decoders and simple function-argument flows. Static analysis is heuristic; source/sink text alone is not a finding.

Script GET requests use the shared sender. Same-origin scripts retain selected request credentials; another origin requires its hostname in enabled Target Scope and receives no captured headers. Redirects are not followed. Scripts are fetched once per task and served to Chrome from captured snapshots with CSP, SRI, MIME and CORS enforcement.

A benign marker is observed first. Sink values guide HTML attribute/element payload choices; code and URL sinks receive JavaScript or javascript: payloads. Browser-only query/fragment mutations preserve the original HTML/scripts. Two independent executions plus non-executing controls are required. Open DOM script audit in a task for source lines, script parse results, candidate excerpts, payload families and limitations. Browser tabs include observed sink values and stacks.

Analysis is bounded to 100 inline units, 16 external script attempts, 256 KB per script, 1 MB external bodies and 40 candidates, with existing duration/evidence limits. Unobserved dependencies, full taint analysis, stateful interactions and stored-XSS workflows remain outside this scope. Unverified paths are inconclusive.

Runtime script dependency discovery

After the first static audit, DOM XSS renders the original URL with its original HTML and captured scripts, even without static candidates. Chromium records blocked main-frame GET script requests, including computed imports and script loaders. It never downloads them directly. Fetch/XHR, images, frames, sockets and navigation are not script downloads.

The shared sender captures eligible dependencies and the engine audits the expanded script set before choosing payloads. Up to three discovery rounds share one quota of 16 script URL attempts and 1 MB of script bodies. Same-origin credentials, explicit Target Scope for other origins, no redirects and existing rate/duration/evidence limits apply. Requests and failures are cached.

Only dependencies from original-URL discovery renders may be fetched. URLs seen in payload renders are evidence only. DOM script audit lists runtime dependencies and analysis notes; Browser tabs show blocked script URLs. Re-audits update one record. A dependency or static flow alone is never a finding: independent executions and negative controls remain mandatory.

The 1.2-second snapshot window does not exercise clicks, long timers, prior storage or application workflows. Missing API responses, scope exclusions and deeper dependency chains can leave paths untested.

Browser interaction

Select DOM XSS (input and event interaction) in an active profile. The script audit identifies supported input-value or URL sources. A benign marker precedes context-selected payloads. Each fresh render can fill one input/textarea and dispatch input/change, then try mouseover, focus and click/input/change on at most 12 interactive elements. Forms are not submitted; browser network remains isolated. CSP is preserved. Independent repeated callbacks and matching benign/original controls are required. Browser evidence records interaction traces.

This is bounded synthetic event exploration, not arbitrary stateful automation. Missing inputs, complex framework gestures, trusted physical events, prior login/storage state and multi-page workflows remain untested.

OAST setup: blind SSRF and XXE

Select Blind SSRF (OAST HTTP/DNS) or Blind XXE (OAST HTTP/DNS) in an active profile. These checks are excluded from Active standard. Slurp includes a separate callback collector, disabled until configured. The callback address must be reachable from the scanned server, not just your browser. API authentication protects issuing/polling probes; the callback listener does not expose the API.

SLURP_OAST_PUBLIC_URL=http://127.0.0.1:8899 \
SLURP_OAST_LISTEN=127.0.0.1:8899 \
./target/debug/slurp --no-open

This example works for targets running directly on the same machine. For LAN/container targets, advertise a reachable IP/hostname and bind the callback listener to the appropriate interface (for example 0.0.0.0:8899). Container loopback is not host loopback. HTTPS requires a TLS reverse proxy preserving /slurp-oast/<id>. Prefix paths require the proxy to strip that prefix.

VariablePurpose
SLURP_OAST_PUBLIC_URLRequired advertised HTTP(S) callback base URL
SLURP_OAST_LISTENHTTP bind; default 127.0.0.1:8899
SLURP_OAST_DNS_DOMAINOptional delegated domain, e.g. oast.example.com
SLURP_OAST_DNS_LISTENUDP DNS bind; default 127.0.0.1:5354; route authoritative UDP 53 to it
SLURP_OAST_DNS_ADDRESSOptional IPv4 A answer pointing to the HTTP collector/proxy

DNS mode uses a unique random-id.domain hostname per probe. Delegate a domain you control or configure equivalent test DNS routing. Wildcard host routing is required, plus a wildcard certificate for HTTPS. Without the A address, DNS can be observed but this responder provides no address for an HTTP connection. DNS is a minimal authoritative UDP service, with no recursive forwarding, TCP or DNSSEC.

SSRF replaces selected query/JSON values with callback URLs. XXE inserts an external parameter-entity DTD into XML bodies; existing DTD/entity and signed documents are excluded. Two independent callback addresses are sent; an unsubmitted control is never sent. Findings require interactions for both probes and none for the control during a 15-second polling window. DNS establishes resolution only. HTTP establishes interaction, not sensitive resource access; findings require review for intermediaries/link scanners. Reflection, timeouts and missing callbacks do not create findings.

OAST evidence tabs show callback URLs, DNS names, timestamps, protocol, peer and request/query detail beside the probe requests/responses. Limits: 1,024 live probes, 16 events per probe, 10-minute memory retention and existing scan budgets. Saved observations persist in the original workspace. Pending state disappears on restart; callbacks after the polling window are not automatically promoted. Persistent background correlation and external collector providers remain planned.

JWT, GraphQL and HTTP protocol

Select the JWT active, GraphQL active or HTTP protocol profile, or choose individual checks in a custom profile.

  • JWT signature verification: signed Bearer JWTs only. Tests changed signatures, none/None/NONE/nOnE algorithm values and missing signatures with unchanged claims. Requires stable successful responses, original-JWT isolation, denied anonymous/malformed-token controls and restored original responses. Public endpoints and status 200 alone are insufficient. Findings need protected-data review. This signature check does not test JWE or role escalation; separate checks cover weak HMAC keys and RSA/HMAC confusion.
  • GraphQL introspection: bounded read-only root-type query, independent repeat and unknown-field error control. Supports captured GET query, JSON POST and application/graphql POST operations. Captured mutations are replaced, never replayed by these GraphQL checks.
  • GraphQL batching: two read-only __typename operations, repeated with a correlated alias and single-operation control. Introspection and batching findings are informational capabilities; authorization and denial of service are not established.
  • HTTP/1 framing: intrusive opt-in; GET endpoints only. Fresh isolated TCP/TLS connections send fixed CL/TE, TE/CL and duplicate conflicting Content-Length variants with ordinary/chunked controls. No application headers or recognized query credentials are sent, and no second request is embedded. Repeated acceptance creates a low-severity review finding, not confirmed smuggling. Timeouts, rejected requests and incomplete responses do not create findings. Four concurrent probes, verified TLS/SNI, pinned DNS, no redirects/proxy/pooling, maximum 10 seconds and 32 KB per raw response. The Request/Response tabs show actual wire evidence. Existing scan budgets still apply.

HTTP/2/3 desync, cross-request smuggling, cache poisoning and GraphQL account-aware authorization/complexity checks remain planned. The protocol profile also includes existing OPTIONS/TRACE and response-header injection checks; select parameters for CRLF tests.

Vulnerable JavaScript dependencies

Choose JavaScript dependencies (OSV) for a captured JavaScript response, or select dependency-audit in a passive profile. Slurp tokenizes up to 256 KB without executing code, recognizes explicit exact stable release banners in comments and checks up to ten package/version pairs. Supported families: jQuery, lodash, AngularJS, Bootstrap, Moment, Vue, React/ReactDOM, Handlebars, Underscore, Axios and DOMPurify. Filenames, generic VERSION values, strings and stripped/versionless bundles are not sufficient attribution.

The backend sends only npm package names and versions to api.osv.dev; source code, target URLs and credentials are never included. Internet access is required for uncached queries. Successful results are cached for one hour; failures remain inconclusive. Fixed upstream, verified TLS, pinned DNS, no proxy/redirects, four concurrent queries, a 12-second deadline and a 2 MB response cap apply.

Findings show package/version, banner evidence, advisory ID, CVE aliases and OSV reference beside the captured response. Withdrawn advisories are excluded. Findings require review: an exact-version advisory match does not establish runtime execution, patch status or exploitability. Unknown versions and no advisory matches do not establish safety. This is a manual scan-profile check; automatic JS endpoint/secret collection is unchanged.

Automatic 403 bypass audit

New proxy API captures returning 403 trigger a backend audit under Target Scope and the Dashboard automatic-audit Pause/Resume control. Existing History is not backfilled. Tasks are named Automatic 403 bypass.

Two original requests must reproduce the captured stable denial. Slurp tests X-Real-IP, X-Client-IP, same-origin Referer, current-path X-Original-URL and X-Rewrite-URL individually. A candidate must return matching nonempty JSON API data twice; a negative header control must remain denied/missing, and the original request must restore the same 403. HTTP 200 alone, HTML/login pages, empty replies and common JSON error envelopes are insufficient. Findings require review and include all request/response controls.

Method, actual endpoint, credentials and body are preserved. Write requests may change application state when a bypass succeeds. No redirect following, path/method changes or forwarded/Host-header probes are performed. Shared sender protections remain in place. Limits: 22 requests, two starts per second and 60 seconds for 403 probes; existing NoAuthen/CORS checks may add two requests if not already completed. Completed checks are deduplicated per workspace and full request/authentication context, including successful retries. Different users are audited independently; inconclusive attempts can retry on later captures. Probe traffic does not re-enter History.

Form inputs, NoSQL and weak JWT signing keys

Parameter-based checks now support application/x-www-form-urlencoded bodies in addition to query and JSON inputs. Select the Form field and duplicate occurrence in the scan dialog. SQL injection, traversal, reflection, browser validation and other scalar checks share this insertion-point support. Only the selected field changes; unrelated encoded segments remain intact. Multipart uploads are not included. Hidden input discovery is available through a separate profile.

The NoSQL parser audit active profile contains two checks. Parser probes require database-specific errors twice, a benign control and original-response restoration; this is not proof of data access. JSON operator checks require a selected string and stable successful JSON data. Two anchored exact-match regex objects must reproduce the original response while independent nonmatching patterns return consistent different data or access denial. The original scalar must restore the baseline. No broad-match operators, JavaScript evaluation or new write operations are introduced by the payloads; the captured request itself may change state. Intentional query DSLs and authorization impact require review.

The JWT weak signing secret (local) passive profile verifies captured Bearer HS256/HS384/HS512 signatures against a small fixed common-secret dictionary using Web Crypto. No token or key leaves the process and no modified token is submitted. A verified finding establishes only that a common key verifies the captured signed bytes; server acceptance and escalation are not tested. Keys are omitted from excerpts. An unmatched dictionary does not establish strong keys. Use localhost or HTTPS for Web Crypto. A separate active check covers RSA/HMAC confusion; arbitrary wordlists and key-source attacks remain planned.

CORS origin validation

The CORS policy profile also tests credentialed null origins and hostnames that contain the target hostname as a prefix or suffix. A finding needs repeated exact ACAO reflection with ACAC: true, preserved baseline content, an unrelated-origin control that is not allowed and original-request restoration. Generic arbitrary-origin reflection and wildcard policies remain covered by the existing CORS check. Findings require browser validation of cookie policy, preflight and response sensitivity; no cross-origin browser access is asserted. Origin payloads are headers only and are never fetched by Slurp.

JWT none algorithms and RSA/HMAC confusion

The JWT signature check tests none, None, NONE and nOnE independently, alongside invalid and missing signatures. Each finding requires repeated authenticated-response equivalence, denied anonymous/malformed controls and restoration of the original JWT. A successful HTTP status alone is insufficient.

Select the JWT algorithm confusion active profile for a captured RS256/RS384/RS512 Bearer JWT. Leave the RSA key field empty to discover public keys using anonymous GET requests to /.well-known/jwks.json, /jwks.json and /.well-known/openid-configuration. A same-origin jwks_uri from discovery is also supported. At most four resources are fetched through the shared bounded Replay sender, with no redirects or captured credentials. Foreign-origin discovery URIs and token-supplied jku/jwk/x5u are not used. Public JWKS availability alone is not a vulnerability.

RSA JWK public components are matched by kid where present and must cryptographically verify the original token before probing. Alternatively, paste an RSA SPKI BEGIN PUBLIC KEY, PKCS#1 BEGIN RSA PUBLIC KEY or X.509 BEGIN CERTIFICATE PEM into scan configuration; private keys are rejected. Slurp tries HS256/HS384/HS512 using bounded SPKI/PKCS#1 PEM (LF/CRLF, optional trailing newline), certificate PEM and DER serializations as the HMAC secret. Claims stay unchanged. Two independently signed tokens must reproduce the isolated original response while anonymous, malformed, invalid-RSA-signature and random-HMAC-key controls are denied. The original RSA response must restore the baseline. Findings retain discovery and probe request/response evidence and require protected-data review.

Cross-origin identity providers require a manually supplied public key. JWKS x5c certificates are supported when their public key matches the verified RSA key. RSA-PSS, ECDSA, key recovery and role escalation are not covered. No matching key is inconclusive, not a clean result. Scan profiles are editable; existing saved JWT profiles can add jwt-confusion or use the new profile.

Discovery and business input validation

The passive Parameter discovery (captured) profile extracts literal parameter-name hints from captured HTML/scripts without fetching URLs. The intrusive Hidden input discovery profile tests a bounded set of hinted/common query, form, root JSON and header inputs. Named-input differences must repeat while random-name and original-request controls remain stable. Discoveries are informational, not vulnerabilities. Crawling, source-map discovery, multipart and path insertion points are not included.

The intrusive Business input validation profile identifies inputs by their values, regardless of field names. Numeric query/form/JSON scalars, including numeric strings and scientific notation, receive negative, zero (repeated), large, fractional and signed-32-bit-boundary probes. JSON numbers remain numbers and numeric strings remain strings. These checks automatically inspect matching inputs within the 100-candidate discovery bound, independently of the manual parameter selection. Successful JSON baselines, two successful probe responses, an original-value control and rejection of a malformed numeric control (400/422) are required.

Returned test values produce low-severity review findings; acknowledgement-only JSON responses produce informational findings because the server may ignore, clamp or normalize values. Recognized JSON error envelopes are excluded. Acceptance alone does not establish persistence or harmful business impact. Optionally expand Business read-back verification in the scan dialog and specify a same-origin GET URL, the input to verify and an exact JSON pointer such as /data/quantity. The captured credentials are reused, conditional headers are removed and cache revalidation is requested. Slurp requires a stable original value, two reads matching each submitted value and a read after original-value restoration. Only then is observed persistence reported at medium severity; intended business rules and impact still require review. One input can be mapped per scan; no resource URL is guessed from write responses. ISO date values receive malformed/impossible-date probes; past dates are tested only when the original date is in the future. These requests can change state: read-back runs only when explicitly configured; replaying the original request attempts value restoration but cannot undo secondary effects or guarantee cleanup. Duration and evidence limits still apply. These profiles are manual scans, not automatic capture audits.

JWT key-source and key-lookup probes

The JWT key-source attacks profile adds embedded jwk, remote jku, remote certificate x5u and intrusive kid checks. Source checks support protected RS256 Bearer tokens and generate an ephemeral RSA key in browser memory; no target public key is needed. The kid check supports HS256/384/512 and tests POSIX null-file lookup and SQL literal key selection without SQL writes. Claims stay unchanged.

Remote jku/x5u checks require the reachable OAST collector configured above. The authenticated key-hosting API publishes only bounded public JWKS/certificates at random callback URLs for up to ten minutes; private keys are never uploaded. Findings require repeated attacker-key token acceptance, denied signature/source controls and restoration of the original protected response. Remote checks also require HTTP fetch correlation and a silent unsubmitted callback control. A callback alone does not establish an authentication flaw. Findings require protected-data review; role escalation is not tested.

Crawl before scanning

In the scan configuration dialog, enable Crawl before scanning and explicitly allow requests. The option is off by default for both passive and active scans; captures and opening the dialog never start a crawl. Default limits are 20 URLs and depth 2, configurable to 1–50 URLs and depth 0–5. The seed counts toward the URL limit.

The HTTP crawler fetches same-origin links, script URLs, GET forms and literal URLs in scripts. It parses up to 256 KB per response without executing scripts. POST forms, password/file fields, common destructive paths and static binary assets are excluded. Target Scope is checked before sends; foreign-origin URLs and redirects are excluded. Shared Replay validation, DNS pinning, bounded responses and no automatic redirects remain in effect. GET endpoints may still change state.

Discovery completes before the selected profile runs sequentially on collected GET endpoints and the original request. Passive checks inspect collected responses; active checks send probes with the selected policy, credentials, rate and timeout. Up to ten discovered scalar inputs per endpoint are selected automatically for parameter-based checks. Business read-back configuration applies only to the original request. Results, endpoint-specific baselines and evidence are retained in one scan task; expand Crawl to see fetched URLs. Existing workspace/temporary persistence rules apply. Crawl requests are not separately imported into HTTP History.

Pause/Stop and workspace changes apply to discovery and its scan stages. The whole task shares duration and evidence limits, so some endpoints may remain untested. URLs sharing a path and query-parameter structure are deduplicated; parameter order/value variations are not exhaustively explored. This is an HTTP crawler, not SPA rendering, authenticated browser interaction or a complete API-method discovery engine.

Automatic CRLF injection audit

New completed proxy captures with supported inputs trigger a background Automatic CRLF injection task after History storage. It runs independently of manual scans/crawls and uses the Dashboard automatic-audit Pause/Resume control and Target Scope. Existing captures are not backfilled. Completed audits are deduplicated by workspace and full request/authentication context, including across restarts; incomplete attempts can retry on a later capture.

Up to four query, form-urlencoded or nested JSON string inputs are tested. Credential-like names, values over 512 bytes and bodies over 16 KB are excluded. Other request values, credentials, method and body are preserved. The worker appends CRLF and percent-encoded CRLF variants using the shared bounded Replay sender, DNS pinning and no redirects. Probes do not enter History or recursively trigger auditing. Repeating state-changing methods may change server state.

A finding requires two independent random markers to appear as an actual X-Slurp-Crlf response header, denied plain-text controls and a restored original request without that header. Body reflection, status changes and transport errors alone never produce findings. Evidence includes the captured response, baseline, payloads, negative controls and restored original; downstream response splitting or cache effects still require review.

Limits: one separate sequential CRLF worker, 128 queued jobs, two starts per second, 60 seconds per audit and at most 34 requests. Other automatic API audits have their own worker. Unsupported inputs, raw path/header injection, multipart and additional encoding families are not covered. No finding does not establish that all CRLF cases are safe.

Host header injection

Select the Host header injection active profile to test Host and X-Forwarded-Host. Two independent .invalid hosts must control actual redirect destinations or absolute URLs in parsed HTML navigation/resource attributes. Plain body reflection is excluded. Unused-marker and restored-original controls reduce false positives. Findings include payloads and request/response evidence and require contextual review.

A separate automatic worker audits captured GET requests with a Location header or own-origin absolute URLs in HTML. Automatic detection currently verifies Location redirects only. Target Scope, automatic-audit pause and workspace/authentication-context deduplication apply. Each audit is bounded to 12 requests and 45 seconds, with at most two starts per second. Probes use no-store/no-cache headers. URL destination, pinned DNS and TLS hostname stay original; redirects are never followed. These observations do not confirm cache poisoning, password-reset poisoning or SSRF.
