Scan dashboard

The dashboard shows running and paused tasks, recent scan history and findings. Use task controls to pause, resume or stop the active scan. Search findings by title or endpoint, filter by severity and status, and choose View evidence to open verification details. Saved findings are paginated and scoped to the selected workspace.

Vulnerability coverage

Slurp ships 72 scan checks: 20 stable, 45 experimental and 7 planned (version 1.1.2). Stable checks are routine observations or have broad verification. Experimental checks are implemented and tested but depend on stable baselines, target behaviour or external tools, so a finding means “verified signal, review the evidence” rather than a confirmed exploit. Planned checks are listed in the catalog but do not run yet. A check marked Automatic also runs in the background on new proxy captures; the rest run only when you start a scan.

Requests shows how much a check sends: Passive sends nothing, Light and Active send bounded probes, and Intrusive may change server state or load and needs both sending and intrusive checks to be allowed in the scan dialog. Uploaded traffic from remote capture clients is not scanned automatically.

Automatic background audits

Besides the checks above, two audits run only in the background on new proxy captures and are described in detail below: Automatic CRLF injection and Host header injection (Location redirects only). Automatic 403 bypass, anonymous API access, CORS, JavaScript endpoint and secret discovery, and the React2Shell, PHP2Shell and HTTP2Shell exposure checks use the same pause control and Target Scope.

Right-click a request in HTTP History, Replay or Intercept and choose Scan passive or Scan active. The full request opens in a configuration dialog above the dashboard. Choosing either action opens configuration; it does not send requests automatically.

Automatic capture audit

New completed proxy captures are audited after History storage, in the backend while Slurp runs. Existing History is not backfilled. Target Scope applies. Dashboard provides a global pause/resume control and queue/completion/skipped/error counters. Automatic auditing is enabled by default; runtime controls reset on restart.

API candidates receive up to two probes: one removes common authentication headers, cookies and token query parameters; the other sets Origin: https://evil.com. Original methods and bodies are retained, so probes can repeat state-changing operations. HTTP 200 produces a NoAuthen finding requiring review. Wildcard or reflected Access-Control-Allow-Origin also requires review; neither alone proves a vulnerability. Body credentials and custom authentication may remain.

Captured JavaScript is analyzed without execution or fetching discovered URLs. Dashboard lists endpoint candidates and suspected usernames/passwords, API keys, tokens and private keys, with source coordinates and masked credential excerpts. Original source and local evidence may still contain secrets. Search findings by endpoint or credential type. Relative URLs and method hints require application context; credentials are not tested for validity.

Captures whose response discloses a PHP release or a PHP session cookie are checked against PHP2Shell (CVE-2026-109618 and CVE-2026-109619). The release is read from X-Powered-By, Server or Via, then from the first 64 KB of the body, and compared with the fixed builds 8.2.35, 8.3.36, 8.4.27 and 8.5.12; end-of-life branches that receive no fix are also reported. The check is passive: it sends no request and attempts no exploit, so an affected version is exposure evidence requiring review, not proof of code execution. When expose_php hides the version, the result is inconclusive. One task per origin and workspace is stored; delete it to audit again.

Captures with a bounded request body (POST/PUT/PATCH, at most 64 KB, not multipart) on a Node.js, Bun, .NET or Brotli-using stack receive one HTTP2Shell probe (CVE-2026-111497). The captured body is resent unchanged with Content-Encoding: br added. A server that applies the encoding rejects the invalid stream, so the status changes from the captured baseline; that shows the native Brotli decoder is reachable from HTTP input. The probe never sends the crafted block-switch payload, so it cannot corrupt memory or execute code, and patched builds answer the same way. Treat the finding as exposure: confirm the runtime and bundled Brotli versions (fixed in Brotli 1.0.10, 1.1.1 and 1.2.1; Node.js 22.23.4, 24.22.1 and 26.12.1). Large, multipart and unrelated stacks are not probed. One probe per origin and workspace is sent; delete the task to repeat it.

Captures of a Next.js or React Server Components response are checked for React2Shell (CVE-2025-55182). The audit looks for Next.js and Flight markers, then sends one ordinary RSC: 1 navigation request; a text/x-component response or Flight rows confirm that RSC is enabled, which the vendor advisory describes as the exposure condition. The probe carries no Server Function payload and no Flight chunk, so it cannot deserialize attacker data or execute code. A positive result is exposure evidence only: confirm the React and Next.js versions in the deployment (affected React 19.0.0, 19.1.0, 19.1.1 and 19.2.0; fixed 19.0.1, 19.1.2 and 19.2.1, plus the patched Next.js releases). Pages Router and non-React stacks are not reported. One probe per origin and workspace is sent; delete the task to repeat it.

Captured GET OAuth authorize requests (client_id with redirect_uri and response_type or an authorize path) are audited automatically. The audit checks whether redirect_uri accepts an attacker origin, tries prefix/suffix bypasses when the plain origin is rejected, reports missing state or nonce, probes response_mode=form_post with a raw-tag state marker, fingerprints the registered callback host only when it shares the site of the identity provider, and reports an ID-token email without email_verified=true. It never uses a code or token, never registers an account and does not test a two-provider mix-up. One audit per origin and client_id is stored; delete the task to repeat it.

Filter/WAF bypass payloads are covered by sql-bypass (comments, newlines, case mixing, versioned comments and UNION obfuscation), xss-bypass (tag alternatives, no-space syntax, entities, keyword splitting, event attributes and javascript: variants) and nosql-bypass (bracketed $regex names in query strings and forms). These checks only prove that a payload reached the SQL parser or was reflected unescaped; they do not execute script, evaluate $where, bypass CSP, exploit sanitizer mXSS or confirm second-order storage.

Template checks cover arithmetic in {{ }}, ${ }, #{ }, <%= %>, *{ } and @( ) syntaxes, an engine fingerprint, and a parser-only polyglot. The intrusive ssti-rce check proves engine execution with the benign id command only; it never runs a shell, reads files or changes data. Test every rendered surface (email/PDF templates, invoice, profile name, subject, error page) by selecting the corresponding parameter.

Command checks cover classic separators, newline/IFS/tab/split-command/base64 filter evasions, and execution-oriented argument injection (git/tar). All proofs execute only id; no reverse shell, file read/write, sleep or external callback is sent. Blind sleep and OAST callbacks remain manual because they slow scans or need a collector, and file-write flags such as --output/-o have no reliable oracle.

Traversal payloads now include single/double encoding, ....//, null-byte suffixes, Windows win.ini/hosts and extended-length paths; inclusion adds expect://id and a remote http://example.com/ fetch. The upload check parses a captured multipart body and varies only filename, part Content-Type and a benign marker body; it never uploads executable code, .htaccess, web.config, archives or traversal filenames. Zip-slip, log poisoning, ImageMagick/EXIF, PDF JS/XXE, SVG/HTML polyglots and CSV formula injection stay manual because they are destructive, stateful or need a file parser.

XXE covers in-band file:///etc/passwd, Windows win.ini and a benign remote http://example.com/ entity with escaped, missing and restored controls. The cloud-metadata payload (http://169.254.169.254/latest/meta-data/) is intentionally not sent automatically because the response could contain instance credentials that would enter scan evidence; use it manually with IMDSv2/authorization and redaction.

Request smuggling / HTTP desync (manual)

Request smuggling exploitation is not automated. The http-framing check only tests acceptance of conflicting framing on isolated fresh connections and does not embed a request or confirm cross-user smuggling. Exploitation requires a raw TCP sender and can leave a prefix on a shared front-end/back-end socket, affecting real users. Test only on staging or an isolated endpoint, with a cache buster, off-peak, and report immediately when a timeout or prefix is observed.

CL.TE: Content-Length: 4 + Transfer-Encoding: chunked with body 1\r\nZ\r\nQ. TE.CL: Content-Length: 6 + Transfer-Encoding: chunked with body 0\r\nX. TE.TE: duplicate/obfuscated Transfer-Encoding (xchunked, chunked + x, tab/space before the colon). H2.CL/H2.TE: send HTTP/2 with content-length: 0 and transfer-encoding: chunked then a downgraded body. Confirm only with a dedicated victim request on staging; never poison production traffic. Cache poisoning starts with an unkeyed header (X-Forwarded-Host, X-Original-URL, X-Forwarded-Prefix, User-Agent) reflected into a cacheable response; cache deception appends static suffixes such as ;.css or %2f.css to an authenticated path.

GraphQL checks cover introspection, field suggestions when introspection is disabled, endpoint discovery and bounded batching/aliases. Field-level authorization, mutation authorization, BOLA via global IDs, GET-based mutation CSRF and alias brute force (OTP) are manual: they read or change other users' data and brute force is abusive. API checks add OpenAPI/Swagger discovery and query-token detection; method override, Content-Type confusion, rate-limit/X-Forwarded-For rotation and version skew remain manual because replay can mutate state.

Prototype pollution is checked in the browser: query/hash payloads (__proto__[x]=1, constructor[prototype][x]=1, a filter-bypass key) are loaded with the captured HTML and the page must expose the property on a fresh object twice. Server-side Node pollution is manual: there is no generic oracle, so safe probe bodies such as {"__proto__":{"slurp_probe":"1"}} and {"constructor":{"prototype":{"slurp_probe":"1"}}} are sent only under a dedicated workflow; RCE gadgets (child_process options, NODE_OPTIONS, template engines, lodash merge) are not executed. Client-side gadgets (jQuery extend, Object.assign, lodash merge/set/defaultsDeep, DOM sinks) still need review.

Open redirect covers //evil, /\evil, target@evil, target.evil, encoded/protocol-relative forms and javascript: Location values; redirects are never followed. postMessage is a static review of the captured HTML: it reports listeners without a visible origin check, DOM sinks near the handler and wildcard targets. It does not post messages or execute handlers; use a browser tracker for delivery testing.

Scan profiles

Choose the separate passive or active action from the request menu, then select a saved profile. Create or edit profiles to choose checks. The engine retains combined Both mode for legacy/programmatic plans. Select parameters for parameter checks. Passive observations now include CSP, HSTS, framing, Content-Type, transport/URL credentials, private-key markers, directory indexes and OpenAPI signatures.

Additional active checks cover repeated SQL error differentials with controls, marked template arithmetic with invalid-syntax controls, parameter-based file traversal with content signatures, and two-destination redirect Location verification. These findings require review. Time or evidence limits can leave remaining checks incomplete. Stored XSS, extended OAST workflows, request smuggling, the full Burp issue catalog is not implemented.

Passive inspects an existing captured response without probing the target; the optional OSV dependency check queries package/version advisories externally. History requests with a response use this mode by default. Cookie checks need separate Set-Cookie fields; collapsed headers are reported as inconclusive.

Active sends repeated baseline, probe and control requests through the Replay sender. Select a scan profile and any required parameters. Advanced request settings contain timing and rate controls. Enable the sending checkbox and click Start scan. Repeated requests may change application state. Requests without an existing response require active mode. HTTP(S), localhost and LAN targets are supported; Replay timeout/response limits apply.

Checks and parameters

  • Cookie flags: observe missing Secure/HttpOnly attributes. Cookie purpose still matters.
  • Response headers: inspect successful HTML documents for nosniff.
  • Error disclosure: look for supported internal-error signatures; example text can cause false positives.
  • Input reflection: test two independent markers in selected inputs. Reflection does not establish XSS.
  • Input error handling: compare stable baselines, malformed input, repeat probe and original-value control. Reproducible errors do not establish injection.
  • CORS origin handling: test two untrusted Origin values. Browser verification is still required.

Reflection and input-error checks require explicit query, form-urlencoded or JSON scalar parameter selections, up to ten. Duplicate query occurrences are listed separately. JSON field names use escaped JSON pointers. Form-urlencoded fields are supported, including duplicate fields; unrelated encoded fields are preserved. Multipart mutations are not supported.

HTTP active checks

Phase 3 adds controlled SQL boolean comparisons, bounded MySQL timing, OAuth redirect_uri strictness and login-chain probes, CRLF response-header injection, anonymous/invalid-credential comparisons, Referer/client-IP trust, URL override routing and bypass (the denied path carried in X-Original-URL or X-Rewrite-URL from the allowed root URL), path normalization and semicolon bypasses, and OPTIONS/TRACE diagnostics. SQL timing is an intrusive check that must be explicitly selected in a profile. Traversal includes additional encoding layers, redirect checks include protocol-relative URLs, and wildcard CORS is a reviewable configuration observation.

Path normalization variants (semicolon, encoded semicolon, parent-segment injection, dot segments and duplicate slashes) require a repeated distinct success, a random-path control and a restored denial; CDN or proxy normalization may differ from the origin. Findings require repeat/control evidence. HTTP 200 alone, reflected body text and timeouts do not establish vulnerabilities. Anonymous access may be intentional; body/custom authentication can remain. URL override reports routing influence, not an authorization bypass. OPTIONS advertising PUT does not trigger a write. TRACE uses diagnostic headers without original application headers. Forwarded/X-Forwarded-* remain filtered; client-IP checks use X-Real-IP/X-Client-IP.

Only method-policy checks may change the selected method to OPTIONS/TRACE, retaining origin/path; CONNECT is unsupported. Anonymous/header-access/method diagnostic responses do not overwrite profile cookies. There is no total request-count limit; review skipped and inconclusive results caused by duration, evidence or check prerequisites. Cross-account BOLA, raw protocol, OAST and stored/browser attack engines are not included.

Run controls

Configure 2–3 baseline samples, a rate of 1–20 starts per second and minimum delay. Known dynamic JSON paths can be excluded from baseline comparison. Pause blocks pending sends. Stop prevents further scheduling; in-flight requests still complete. App navigation keeps the run alive, while changing workspace stops scheduling. Keep the browser open; unfinished scans do not survive reload.

Read results

Severity and confidence are separate. Verified refers only to the observation named in the finding and its recorded verification method. Suspected indicates a signature that needs confirmation. Needs review requires contextual or browser validation. Check skipped and inconclusive results even when there are no findings; absence of findings does not establish security.

Expand a finding for its explanation, verification method, excerpts, remediation and evidence. Request evidence supports the context menu, including Send to Replay and Copy cURL. Expand request/response panels to search their contents or compare a response with the baseline.

Evidence includes actual requests and credentials and is stored locally with the selected workspace. Response previews are bounded and truncation is shown. The engine has an 8 MB evidence budget and stops before sending requests it cannot retain. Saved run history can be selected, paginated and deleted. Temporary runs remain in browser memory.

A failed save can be retried with Retry evidence saving; it writes the captured evidence without sending HTTP requests again.

Browser XSS validation (phase 5, initial scope)

Uncaptured secondary traffic and frames are blocked; the DOM check can use captured script snapshots; cookies and prior browser state are not reused. This initial scope covers selected HTML/attribute/script-string contexts and inline-script DOM paths. Full taint analysis, dependencies outside bounded runtime discovery, user interactions and stored-XSS write/readback/cleanup workflows remain planned. Negative snapshot results are inconclusive for those paths.

DOM script audit before probing

The DOM XSS check first parses executable inline scripts and script files, follows bounded literal module imports and identifies URL source/sink candidates. It recognizes query names from URLSearchParams, selected aliases/decoders and simple function-argument flows. Static analysis is heuristic; source/sink text alone is not a finding.

Script GET requests use the shared sender. Same-origin scripts retain selected request credentials; another origin requires its hostname in enabled Target Scope and receives no captured headers. Redirects are not followed. Scripts are fetched once per task and served to Chrome from captured snapshots with CSP, SRI, MIME and CORS enforcement.

A benign marker is observed first. Sink values guide HTML attribute/element payload choices; code and URL sinks receive JavaScript or javascript: payloads. Browser-only query/fragment mutations preserve the original HTML/scripts. Two independent executions plus non-executing controls are required. Open DOM script audit in a task for source lines, script parse results, candidate excerpts, payload families and limitations. Browser tabs include observed sink values and stacks.

Analysis is bounded to 100 inline units, 16 external script attempts, 256 KB per script, 1 MB external bodies and 40 candidates, with existing duration/evidence limits. Unobserved dependencies, full taint analysis, stateful interactions and stored-XSS workflows remain outside this scope. Unverified paths are inconclusive.

Runtime script dependency discovery

After the first static audit, DOM XSS renders the original URL with its original HTML and captured scripts, even without static candidates. Chromium records blocked main-frame GET script requests, including computed imports and script loaders. It never downloads them directly. Fetch/XHR, images, frames, sockets and navigation are not script downloads.

The shared sender captures eligible dependencies and the engine audits the expanded script set before choosing payloads. Up to three discovery rounds share one quota of 16 script URL attempts and 1 MB of script bodies. Same-origin credentials, explicit Target Scope for other origins, no redirects and existing rate/duration/evidence limits apply. Requests and failures are cached.

DOM script audit lists runtime dependencies and analysis notes; Browser tabs show blocked script URLs. Re-audits update one record. A dependency or static flow alone is never a finding: independent executions and negative controls remain mandatory.

The 1.2-second snapshot window does not exercise clicks, long timers, prior storage or application workflows. Missing API responses, scope exclusions and deeper dependency chains can leave paths untested.

OAST setup: blind SSRF and XXE

Select Blind SSRF (OAST HTTP/DNS) or Blind XXE (OAST HTTP/DNS) in an active profile. These checks are excluded from Active standard. Slurp includes a separate callback collector, disabled until configured. The callback address must be reachable from the scanned server, not just your browser. API authentication protects issuing/polling probes; the callback listener does not expose the API.

SLURP_OAST_PUBLIC_URL=http://127.0.0.1:8899 \
SLURP_OAST_LISTEN=127.0.0.1:8899 \
./target/debug/slurp --no-open

This example works for targets running directly on the same machine. For LAN/container targets, advertise a reachable IP/hostname and bind the callback listener to the appropriate interface (for example 0.0.0.0:8899). Container loopback is not host loopback. HTTPS requires a TLS reverse proxy preserving /slurp-oast/<id>. Prefix paths require the proxy to strip that prefix.

VariablePurpose
SLURP_OAST_PUBLIC_URLRequired advertised HTTP(S) callback base URL
SLURP_OAST_LISTENHTTP bind; default 127.0.0.1:8899
SLURP_OAST_DNS_DOMAINOptional delegated domain, e.g. oast.example.com
SLURP_OAST_DNS_LISTENUDP DNS bind; default 127.0.0.1:5354; route authoritative UDP 53 to it
SLURP_OAST_DNS_ADDRESSOptional IPv4 A answer pointing to the HTTP collector/proxy

DNS mode uses a unique random-id.domain hostname per probe. Delegate a domain you control or configure equivalent test DNS routing. Wildcard host routing is required, plus a wildcard certificate for HTTPS. Without the A address, DNS can be observed but this responder provides no address for an HTTP connection. DNS is a minimal authoritative UDP service, with no recursive forwarding, TCP or DNSSEC.

SSRF replaces selected query/JSON values with callback URLs. XXE inserts an external parameter-entity DTD into XML bodies; existing DTD/entity and signed documents are excluded. Two independent callback addresses are sent; an unsubmitted control is never sent. Findings require interactions for both probes and none for the control during a 15-second polling window. DNS establishes resolution only. HTTP establishes interaction, not sensitive resource access; findings require review for intermediaries/link scanners. Reflection, timeouts and missing callbacks do not create findings.

OAST evidence tabs show callback URLs, DNS names, timestamps, protocol, peer and request/query detail beside the probe requests/responses. Limits: 1,024 live probes, 16 events per probe, 10-minute memory retention and existing scan budgets. Saved observations persist in the original workspace. Pending state disappears on restart; callbacks after the polling window are not automatically promoted. Persistent background correlation and external collector providers remain planned.

JWT, GraphQL and HTTP protocol

Select the JWT active, GraphQL active or HTTP protocol profile, or choose individual checks in a custom profile.

  • JWT signature verification: signed Bearer JWTs only. Tests changed signatures, none/None/NONE/nOnE algorithm values and missing signatures with unchanged claims. Requires stable successful responses, original-JWT isolation, denied anonymous/malformed-token controls and restored original responses. Public endpoints and status 200 alone are insufficient. Findings need protected-data review. This signature check does not test JWE or role escalation; separate checks cover weak HMAC keys and RSA/HMAC confusion.
  • GraphQL introspection: bounded read-only root-type query, independent repeat and unknown-field error control. Supports captured GET query, JSON POST and application/graphql POST operations. Captured mutations are replaced, never replayed by these GraphQL checks.
  • GraphQL batching: two read-only __typename operations with a single-operation control, plus one read-only operation carrying 20 __typename aliases, each repeated. Alias batching multiplies per-request work and can bypass throttling that counts only HTTP requests. Introspection and batching findings are informational capabilities; no brute force, depth or load test is performed, and authorization or denial of service is not established.
  • HTTP/1 framing: intrusive opt-in; GET endpoints only. Fresh isolated TCP/TLS connections send fixed CL/TE, TE/CL and duplicate conflicting Content-Length variants with ordinary/chunked controls. No application headers or recognized query credentials are sent, and no second request is embedded. Repeated acceptance creates a low-severity review finding, not confirmed smuggling. Timeouts, rejected requests and incomplete responses do not create findings. Four concurrent probes, verified TLS/SNI, pinned DNS, no redirects/proxy/pooling, maximum 10 seconds and 32 KB per raw response. The Request/Response tabs show actual wire evidence. Existing scan budgets still apply.

HTTP/2/3 desync, cross-request smuggling, cache poisoning and GraphQL account-aware authorization/complexity checks remain planned. The protocol profile also includes existing OPTIONS/TRACE and response-header injection checks; select parameters for CRLF tests.

Vulnerable JavaScript dependencies

JWT none algorithms and RSA/HMAC confusion

Automatic CRLF injection audit
